## A. Hermes Desktop shutdown on launch (FIXED)

### Symptom
User observed: "everything odysseus is launched and tested that hermes desktop gets shutdown sometimes."

### Root cause (confirmed)
`Get-OdysseusProcesses` (`launch-windows.ps1`) matched `uvicorn | app:app | odysseus | <repo-root>`. `Stop-OdysseusProcesses` runs at every launch to clear stale procs. The matcher caught Hermes-owned processes (anything with "odysseus" in cmd line, or running under the repo dir) and killed them, tearing down Hermes Desktop. Identical matcher in `reset.ps1`.

### Fix
- Match only: (a) cmd line containing the venv python path **and** `uvicorn app:app`; (b) venv `chroma.exe`.
- Explicitly **exclude** any process whose executable resolves into `%LOCALAPPDATA%\hermes\hermes-agent`.
- Dropped bare `odysseus` and repo-root substring matches.
- PS 5.1 `Where-Object` `return`-early quirk fixed: use `$true; return` / `$false; return` (a bare `return $true` exits the scriptblock and emits nothing — would have made the fix a silent no-op).

### Verification (live)
- Both scripts parse clean (PS 5.1 AST).
- Behavioral test (synthetic): 7/7 pass.
- Live process-list proof: `Get-OdysseusProcesses` catches the 2 running Odysseus server PIDs, matches **0** of 19 live Hermes processes. `reset.ps1` matcher: same (2 caught, 0 Hermes).

### Status
Fixed in `launch-windows.ps1` and `reset.ps1`. Verified against the live system. Awaiting commit/push.

## C. ChromaDB server never starts (P1 — FIXED)

### Evidence (live + app.log)
- `data/logs/app.log` showed repeated every-launch errors: `VectorRAG init failed: ChromaDB is not reachable at localhost:8100`, `MemoryVectorStore init failed`, `ToolIndex init failed`.
- `venv/Scripts/chroma.exe` was **MISSING**; `127.0.0.1:8100` not listening; `chromadb-client` 1.5.9 installed (client only, no server binary).

### Root cause
`Ensure-ChromaDbPackage` only verified/installed `chromadb-client` (HTTP client, no `chroma.exe`). `Start-OdysseusChromaDb` got a null exe → server never started.

### Fix applied (launch-windows.ps1 `Ensure-ChromaDbPackage`)
Now installs the **full `chromadb` package** (provides `chroma.exe`) via the mirror when the server binary is missing, then returns the exe path so the launcher starts it.

### Verification (live)
- `pip install chromadb` via Tsinghua mirror → success, `chroma.exe` present.
- Started `chroma.exe run --host 127.0.0.1 --port 8100` → log: "Frontend server listening on address, addr: 127.0.0.1:8100". Confirmed listening.
- launch-windows.ps1 parses clean.

### Fix applied (routes/cookbook_routes.py)
`_check_hf_reachable(repo_id, hf_token)` pre-flight in `model_download` (local HF downloads), probing `api/models/{repo_id}`.

### Verification (live control cases)
