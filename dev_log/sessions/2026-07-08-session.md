## B. Hermes Desktop shutdown fix (APPLIED + VERIFIED, uncommitted)

### Root cause
`Get-OdysseusProcesses` (launch-windows.ps1) matched `uvicorn | app:app | odysseus | <repo-root>`. `Stop-OdysseusProcesses` runs at every launch (line 435) → killed Hermes-owned processes → Hermes Desktop shut down. Identical matcher in `reset.ps1` (line 22).

### Fix
- launch-windows.ps1 + reset.ps1: matcher now matches only (a) cmd line containing venv python path **and** `uvicorn app:app`, (b) venv `chroma.exe`; **excludes** any process whose exe resolves into `%LOCALAPPDATA%\hermes\hermes-agent`. Dropped bare `odysseus` + repo-root substring.
- PS 5.1 quirk fixed: `Where-Object` predicates use `$true; return` / `$false; return` (a bare `return $true` exits the scriptblock early and emits nothing — would have made the fix a silent no-op).

### Verification (live)
- Both scripts parse clean (PS 5.1 AST). Behavioral test 7/7. Live process-list proof: `Get-OdysseusProcesses` catches 2 running server PIDs, matches **0** of 19 live Hermes procs. reset.ps1 matcher: same.

### Status: verified, NOT committed.

## C. ChromaDB server never starts (P1 — FIXED, uncommitted)

### Root cause (live + app.log)
`app.log` showed repeated every-launch errors: `VectorRAG init failed: ChromaDB is not reachable at localhost:8100`, `MemoryVectorStore init failed`, `ToolIndex init failed`. `venv/Scripts/chroma.exe` was MISSING; 8100 not listening; `chromadb-client` 1.5.9 present (client only, no server binary). `Ensure-ChromaDbPackage` only installed `chromadb-client`, so `Start-OdysseusChromaDb` got null exe → server never started.

### Fix (launch-windows.ps1 `Ensure-ChromaDbPackage`)
Now installs the **full `chromadb` package** (provides `chroma.exe`) via `ODYSSEUS_PIP_MIRROR` when the server binary is missing, then returns the exe path so the launcher starts it.

### Verification (live)
- `pip install chromadb` via Tsinghua mirror → success, `chroma.exe` present.
- Started `chroma.exe run --host 127.0.0.1 --port 8100` → log: "Frontend server listening on 127.0.0.1:8100". Confirmed listening.

### Status: fixed, NOT committed.

## D. HuggingFace download silent failure (P2 — FIXED + CORRECTED, uncommitted)

First probe used `HEAD .../resolve/main/config.json`. That returns 404 for BOTH valid GGUF repos (many have no config.json) AND non-existent repos → would have wrongly **blocked good downloads**. Also initially concluded "HF is network-blocked" from two 401 repos; a control test (`gpt2` → 200) disproved that.

### Corrected findings (control-tested)
- HF IS reachable from this host: `gpt2` → 200, valid GGUF `Qwen/Qwen2.5-0.5B-Instruct-GGUF` → 200, and the user's `unsloth/Qwen3.5-2B-GGUF` → **200 (the repo EXISTS)**.
- So the user's original `unsloth/Qwen3.5-2B-GGUF` failure was NOT "missing repo." Real cause unconfirmed (likely `include=*Q4_K_M*` filter mismatch, transient error, or hf_transfer crash near end). P2 no longer wrongly blocks it.

### Fix (routes/cookbook_routes.py)
Added `_check_hf_reachable(repo_id, hf_token)` pre-flight in `model_download` (local HF downloads), probing `GET https://huggingface.co/api/models/{repo_id}`: 200 = proceed; 401/403/404 = clear error (no download); network error = don't block.

## Lessons learned this session (per critique)
- Control-test before root-cause: test a known-good baseline (e.g. `gpt2` → 200) before claiming "blocked."
- Dry-run trace PS filter/pipeline logic (Where-Object/return no-op class).
- Write scripts to `.ps1` files, not inline bash→PS one-liners (bash mangles quoting).
- State test coverage ("what did this NOT test") before declaring done.
- `Join-Path` 5.1 = 2 args only; match Windows processes on command line not ExecutablePath; `taskkill /F /IM` beats `Stop-Process`.
